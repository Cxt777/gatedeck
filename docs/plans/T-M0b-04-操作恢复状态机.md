- 任务 ID / 任务名 / 目标：T-M0b-04｜操作恢复状态机（跨文件四相）｜prepared→applied→logged→committed/aborted，逐中断点可恢复，不留状态与日志不一致（P-06 / B-2）。

- 不做什么：不做真实落盘/日志追加（IO 属 CLI 层）；不做自动回滚已写文件（追加式前向恢复，回滚需人工确认）；不定义 journal 的磁盘格式（M1 `pm init` 契约任务）。
- 风险点：恢复判断只能依赖调用方注入的盘上观察与「日志是否存在」三值（存在/不存在/未知）；未知不得当作存在——如实标注并进「需处理」。
- 红线自检：P-01（journal 为操作材料，业务事实仍在 Markdown）、P-02（恢复只追加，不改写日志）、P-06（四相 + 中断保留材料）、B-2。

## 【计划】具体实施的计划

- 步骤分解（按依赖顺序，每步标注产物）：
  1. 定义 journal（operation_id / phase / targets[path, baseHash, nextHash] / event_id / 时间戳由调用方注入）；
  2. 相位迁移函数 `markApplied` / `markLogged` / `commitOperation` / `abortOperation`，非法迁移拒绝（不静默跳到下一相）；
  3. `assessRecovery(journal, observations, { eventLogged })`：按相位 + 每目标状态（base/applied/conflict）给出 `noop / resume-apply / resume-log / commit / abort / manual-review`，并输出待重试文件、冲突文件、需处理标志；
  4. 中断点注入测试：prepared 未写、prepared 部分写、applied 未记日志、applied 日志已写未推进、logged 未提交、committed、外部冲突、logged 后文件被外部改回、非法迁移、日志存在性未知。
- 角色分工：AI 负责实现与测试；主理人仅需在 G-M0b 过目恢复决策表。
- 验证手段：`pnpm typecheck` + `pnpm test` + `pnpm lint`；B-2 样本入回归。
